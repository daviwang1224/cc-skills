# KMMOM 标准业务方案评审基线

本文件只回答一个问题：**为什么某项业务流程、业务场景或业务规则应该进入 KMMOM 标准产品，或者不应该进入。**

它提供产品战略和业务判断依据，不提供逐项检查步骤。具体如何检查由 `process-scenario-review-rubric.md` 规定。

## 1. 总体判断逻辑

评审不是从客户需求直接跳到产品功能，而是沿着以下逻辑推导：

1. 明确 KMMOM 服务的目标市场和产品方向；
2. 判断内容是否属于完整 MOM 应承担的制造运营职责；
3. 判断它在当前业务域中是否构成必要业务闭环；
4. 从客户具体做法中提炼稳定业务不变量；
5. 根据稳定性、闭环必要性和复用价值确定承载位置；
6. 用核心状态、正式业务操作、API、事件和数据语义守住产品边界；
7. 让项目差异在受治理的机制中实现，并将经过验证的经验持续沉淀。

这条逻辑必须整体使用。不能只强调“标准产品守共性”而留下产品缺口，也不能只强调“业务必须闭环”而把客户全部做法吸收进核心产品。

## 2. 产品战略前提

### 2.1 目标市场和产品愿景

KMMOM 聚焦高端离散制造，重点服务央国企和大型制造集团，不追求覆盖所有制造行业，也不走面向中小企业的轻量套件路线。

产品愿景是：**做最懂工艺、最适合高端离散制造的 MOM。**

因此，“跨客户共性”的范围是 KMMOM 的目标客户群，而不是所有制造企业。某项能力不适用于流程制造或中小企业，并不必然意味着它不能成为 KMMOM 标准能力。

高端离散制造通常具有多品种、小批量、特殊要求多、产品结构复杂、制造周期长、质量和追溯要求高等特点，并可能同时包含铸造、锻造、机加、焊接、热处理、装配、调试和修理等专业。标准产品要覆盖这些专业共享的制造运营主线，同时允许专业差异在核心之外存在。

### 2.2 以工艺为根

KMMOM 的工艺特色不是增加若干工艺页面，而是以工艺为主线连接设计、工艺和生产执行：

- 从工程系统接收产品、工艺、资源和版本要求；
- 让正确的工艺要求进入计划、任务和现场作业；
- 控制现场使用正确的版本、顺序、参数、资源和质量要求；
- 处理工艺变更对在制任务和后续执行的影响；
- 采集实际执行、物料、质量和资源数据；
- 形成过程反馈和制造追溯；
- 在适用时将执行结果反馈给工程或工艺改进活动。

工艺特色最终必须转化为客户能够感知的结果，例如工艺要求执行更准确、工艺变更落地更及时、制造过程追溯更完整。与当前业务域无关时，不为突出特色强行加入工艺内容。

### 2.3 产品建设取舍

KMMOM 产品建设遵循以下统一取舍：

- 客户价值必须进入真实流程并持续支撑业务运行；
- 核心业务场景要做深，不以功能数量衡量产品水平；
- 跨客户稳定、语义清晰、值得长期维护的能力进入标准产品；
- 易用、稳定、性能、可交付、可维护和可升级与业务功能同等重要；
- 产品投入应同时具有客户价值、市场价值和复用价值；
- 通过标准化、资产复用和交付效率形成长期盈利；
- 不因单一客户机会无限扩张产品范围；
- 不用产品碎片化换取短期签单和一次性交付便利。

标准产品做减法，减掉的是客户专属逻辑对核心版本的侵入，不是标准产品应有的业务完整性。

## 3. 完整 MOM 的产品含义

### 3.1 MOM 的业务边界

MOM 面向 ISA-95 Level 3 制造运营活动：

- 向上连接 ERP 等计划和经营系统；
- 与 PLM、MPM 等工程系统交换产品、工艺和资源定义；
- 向下与设备联网、过程监控和现场控制系统协同；
- 在生产、质量、维护和库存等活动中贯通计划、调度、执行、跟踪和分析。

ERP、PLM、MPM、SRM、CRM、工业物联网和专业控制系统具有自己的职责。KMMOM 通过正式输入输出、API 和业务事件与它们协同，不复制对方内部业务，也不把所有相邻问题纳入产品。

### 3.2 MOM 不是功能集合

单独具备下列内容不能证明产品已经形成 MOM：

- 生产数据采集；
- 审批流程；
- 页面、表单和工作台；
- 设备看板；
- 报表和大屏；
- 数据模型和接口框架；
- 单一生产执行工具。

完整 MOM 要把生产组织方式、业务流程、管理规则、现场执行和运营数据连接起来。产品功能只有进入现场流程、控制业务运行并形成结果，才转化为客户价值。

### 3.3 双层业务闭环

完整性分为两个层次：

#### 业务域内部闭环

当前业务域必须从明确输入和触发出发，围绕核心业务对象完成必要的计划、任务、执行、控制、实际反馈、状态变化、异常处理和结果输出。具体活动因业务域不同而变化，但不能把实现业务价值所必需的主线交给项目补齐。

#### MOM 跨域协同闭环

当前业务域还必须明确从其他业务域或外部系统接收什么、自己拥有和控制什么、向后续活动输出什么。单一质量方案不需要包含完整维护流程，单一库存方案也不需要复制生产全过程；它们需要自身闭环，并在 MOM 整体中形成清晰的责任和输入输出。

### 3.4 综合覆盖、分层建设

KMMOM 采用综合型离散制造 MOM 路线：

- 覆盖离散制造主要业务闭环和主要专业；
- 每个业务领域形成标准业务方案；
- 建设深度根据项目频度、客户价值、既有基础和专业差异分层确定；
- 不收缩为只能解决局部问题的专业工具；
- 不扩张为无边界的企业管理平台。

评审不同业务域时，可从以下制造运营活动理解其整体位置：

- 生产运营：定义和资源准备、计划或调度、任务派发、作业执行、实际反馈、在制跟踪、绩效和追溯；
- 质量运营：质量要求或检验计划、检验任务、结果、不合格控制、处置、复检、质量状态和追溯；
- 维护运营：设备或资产、维护策略、请求、工单、任务执行、故障、备件和工时反馈、验收和绩效；
- 库存与物料运营：物料和库存单元、分配或预留、收发退、移动、批次或序列、状态控制、账实一致和追溯。

这些活动是理解 MOM 整体的视角，不是要求每份单一业务方案全部覆盖。

## 4. 标准业务方案的产品化职责

产品标准业务方案面向一个相对完整的业务领域，是产品设计和项目定制共同依赖的上游业务基线。

它同时承担两项职责：

1. **定义标准业务蓝图**：说明标准产品必须提供的目标、范围、流程、场景、规则和结果；
2. **规划企业差异支持**：说明哪些变化由产品配置承接，扩展应用需要调用什么标准业务能力、订阅什么业务事实。

业务方案不是通用知识介绍、单客户现状、项目需求清单、页面字段清单、接口契约或技术架构。客户名称、专属组织、岗位、审批层级、编码、报表、页面习惯和项目过渡方案不能直接成为标准结论。

标准业务方案的内容形成一条产品化链路：

**目的 → 范围 → 标准流程 → 业务场景 → 业务规则与结果 → 企业差异支持。**

后续功能模块和业务对象从这条稳定链路继续推导，但不属于本 Skill 的评审输出范围。

单客户材料可以提供候选问题和实际经验，但进入标准方案前必须去掉客户身份和实现习惯，转换为通用角色、业务对象、规则、状态和结果，并说明复用依据。

## 5. 共性与差异的归属模型

### 5.1 先识别业务不变量

客户说出的通常是具体做法，标准产品需要识别做法背后的稳定业务问题。

- **业务不变量**：稳定的业务目的、核心对象、必要活动、核心规则、状态和结果；
- **业务变量**：组织、岗位、审批层级、编码、页面、报表、阈值、触发策略和操作习惯。

正确的抽象过程是：

**客户具体做法 → 本质业务问题 → 稳定不变量 → 变化维度 → 承载位置。**

抽象不能停在两个错误层次：

- 过度具体：仍然保留客户部门、岗位、三级审批和专属页面；
- 过度抽象：只剩“赋能、协同、系统处理、智能管理、灵活支持”等空泛表述。

### 5.2 共性不能只靠客户数量判断

“多个客户提出”不是共性的充分条件，“只有一个已知案例”也不是否定共性的充分条件。应综合判断：

- 业务语义、对象和目的是否稳定；
- 是否属于目标市场反复存在的制造运营问题；
- 是否是标准产品独立完成闭环的必要原则；
- 是否涉及需要统一维护的核心状态、规则和追溯；
- 客户之间变化的是业务本质还是实现方式；
- 是否有标准、多个项目、稳定模型或专业判断支持；
- 进入产品后是否值得长期统一维护；
- 是否会导致配置组合、测试和升级复杂度失控。

多个客户都有审批，只能证明审批机制常见，不证明审批角色和层级具有共性。多个客户都有报表，也不证明每张报表都应进入标准核心。

### 5.3 承载位置

#### KMMOM 标准产品核心

适合承载：

- 跨目标客户稳定的标准业务主线；
- 完成客户价值闭环不可缺少的活动；
- 核心业务对象和稳定关系；
- 核心状态、流转条件和正式业务操作；
- 需要统一保证一致性、完整性和追溯性的规则；
- 适用于当前业务域的工艺与制造运营连接；
- 面向扩展应用发布的正式业务能力和业务事实。

#### 产品内置配置

适合承载不改变业务本质的变化：

- 业务参数和受控策略；
- 编码规则；
- 权限和数据范围；
- 页面布局和显示；
- 审批流程。

配置必须有生效范围和不可突破的边界，不能任意改变核心规则和核心状态。

#### KMCDAP 差异扩展

KMCDAP 是 KMMOM 的差异承接和应用扩展平台，技术上可以独立建设，产品战略上从属于 KMMOM。差异按四层承接：

1. KMMOM 内置扩展；
2. 平台低代码应用，用于页面、表单、流程、工作台、看板、报表、数据集成和轻量辅助应用；
3. 平台高代码应用，用于复杂逻辑、专业算法、深度集成、高性能处理或完整独立应用；
4. 平台外部技术体系，用于客户既有平台、指定技术栈、第三方产品或自有平台无法合理承载的服务。

所有扩展都必须通过正式 API、业务事件、消息或受控数据交换与 KMMOM 协同，不能直接修改内部数据、复制核心逻辑或绕过核心状态控制。

#### 单客户项目

客户专属组织、岗位、审批层级、编码、页面、报表、操作习惯、临时规则、历史兼容和过渡方案，在没有复用证据时保留在项目范围。

#### 外部系统或相邻业务域

其他系统或业务域拥有的职责保留在其边界内。KMMOM 只定义正式输入、输出和协同关系。

#### 证据不足

证据不足时不能凭推测强行归属。应说明当前可以确认的稳定内容、缺少的证据和需要联合判断的问题。

### 5.4 归属会随验证演进

归属不是一次性决定：

- 多客户验证且业务语义稳定的能力可以进入 KMMOM；
- 在专业、行业或场景中反复出现的差异可以形成模板；
- 只服务当前客户的内容继续保留在项目；
- 无法维护、已经失效或不再符合产品边界的模板应退出。

模板不是历史项目源码的复制件，而是经过业务抽象、产品化整理和项目验证的可复用资产。模板可以包括页面区块、流程、规则、接口适配器和公共组件，也可以是独立解决一个专业问题的应用模板，或由多个专业应用组合形成的行业方案。

模板不能拆成大量没有独立业务语义的零散功能，也不能大到重新形成一套包含所有客户差异的行业产品。项目成果进入模板前必须：

- 删除客户名称、专属组织和特殊数据；
- 提炼稳定业务场景和允许调整的部分；
- 改为依赖 KMMOM 正式 API、业务事件和扩展机制；
- 明确适用条件、产品版本、安装方式和维护责任；
- 经过整理和项目验证。

没有明确场景、适用条件、产品依赖和项目验证的内容不能成为正式模板。新项目应先确认标准产品覆盖，再选择已有模板，只开发剩余差异；项目结束后重新判断新增成果的归属。

### 5.5 典型推导：首件检验

首件检验能够说明标准原则和专业差异如何分层：

- 稳定业务原则是：满足首检条件时形成首检任务，首检未完成或未通过时，后续生产不能正式放行；
- 首检任务、检验结果、核心状态和生产放行应由 KMMOM 统一掌控；
- 按订单、批次、换型、换设备或换工装触发，以及检验内容和确认方式，可能因专业和企业不同而变化；
- 在机加、装配等专业中反复出现的触发和执行方式，可以形成受治理的配置或应用模板；
- 当前客户剩余的特殊要求保留在项目范围。

这不是首检专属规则，而是一种通用推导方法：**标准产品掌控稳定业务原则和核心状态，平台复用专业差异，项目承接客户剩余差异。**

## 6. 不可突破的产品治理边界

### 6.1 核心状态和正式业务操作

核心业务对象和状态是不同场景衔接的稳定基础，必须由标准产品统一维护。

审批只决定业务是否允许继续。正确关系是：

**标准产品发起审批 → 审批返回结果 → 标准产品校验业务条件 → 标准产品执行正式业务操作 → 标准产品更新核心状态。**

配置、审批流、定制应用和外部系统不能直接修改核心状态。需要改变状态时，必须调用标准业务能力，由产品完成权限、规则、状态和数据完整性校验。

### 6.2 统一业务语义

跨模块应保持统一、稳定、可扩展的业务语义：

- 同一业务对象不能因模块或项目不同而重复定义；
- 对象命名、状态约束、追溯规则和建模风格保持一致；
- 不把项目字段简单汇总进公共对象；
- 核心数据由拥有职责的标准业务能力修改；
- 模块、服务和定制应用不能无边界地修改其他业务对象。

### 6.3 标准 API 和业务事件

- 标准 API 表达完整业务查询或业务操作，不是数据库增删改查；
- 标准产品通过 API 执行权限、规则、状态和完整性校验；
- 标准业务事件表达已经发生、有业务意义且订阅方有处理价值的事实；
- “数据已变化、字段已更新、页面操作完成”不是合格业务事件。

业务方案阶段只说明所需业务能力、业务事实和用途，不展开 URL、HTTP 方法、报文和事件载荷。

### 6.4 控制配置复杂度

将所有差异做成配置，不会消除复杂度，只会把定制复杂度转移进标准产品，形成大量组合、测试和升级风险。拒绝所有差异同样不能解决客户问题。

正确做法是：标准产品保持完整、清晰和稳定；允许变化的内容受控配置；可复用差异进入平台和模板；单客户差异留在项目。

## 7. 生态和长期演进

产品战略的完整表达是：**产品守共性，平台承变化，客户伙伴共建生态，共同为客户创造长期价值。**

其含义是：

- 客户最了解自身特殊性，产品团队必须更了解跨客户稳定共性；
- 产品团队提供完整标准主线、稳定语义、开放能力和治理规则；
- 平台提供低代码、高代码、运行环境和资产复用机制；
- 项目团队、客户和伙伴在正式边界内建设贴近自身场景的能力；
- 项目经验经过抽象、整理和验证后反哺产品或模板。

如果所有差异只能由原厂从零开发，产品规模化会退化为人力服务规模化。如果平台没有正式 API、事件和状态边界，生态应用也无法安全建设。

在 APS、IoT 等 KMMOM 不具天然优势的专业领域，可以与高校、专业伙伴或客户既有技术力量协同。守住制造运营主线，不等于独占客户所有问题的解决方式。

产品建设需要保持克制：不对客户要求照单全收，不把所有差异都做成配置，不以平台存在为理由留下产品缺口。评审最终要保护的是标准主线、产品质量、交付复制、版本升级和长期维护能力。

## 8. 开目产品底色和证据边界

KMMOM 的产品底色包括：

- 长期面向离散制造和复杂装备制造；
- 核心积累集中在产品、工艺与制造执行的连接；
- 典型问题涉及多品种小批量、复杂工艺、长周期、严质量、强追溯和多系统协同；
- 公开项目经验涉及航空、装备、修理等场景，以及生产、质量、物料、设备、现场数据和追溯。

这些经验用于理解目标行业和识别候选场景，不能代替共性证据：

- 历史 eCOL MES 或项目案例不能自动等同于当前 KMMOM 标准能力；
- 单一客户做法不能直接成为标准结论；
- 匿名客户必须保持匿名；
- 厂商产品页只能证明公开定位，不能证明每项能力的实现深度和成熟度；
- 专业领域证据不足时，应明确标记未知，等待后续经过项目验证的领域模式扩展。

公开来源和证据使用规则见 `source-evidence-register.md`。
